# Code and requirements review, 2026-09-26

Review of `main` at `308705e` (0.1.1). Every source file and doc was read. The baseline for requirements is the README and `docs/`; there is no other spec.

Gates at review time: ruff clean, pyright 0 errors, 60 tests pass.

Items marked **[repro]** were reproduced with `scripts/review_repro.py`. Run one check with `.venv/bin/python scripts/review_repro.py r2`, or all of them with no arguments. Line numbers refer to `308705e`.

## How to use this list

- Work in the order under [Fix order](#fix-order). The H items are small and local.
- Each item has an **Acceptance** line. Turn it into a regression test in `tests/` before or alongside the fix. The repro script shows the shape of the test but it is not a test suite.
- The shared fixture in `tests/conftest.py` sets `max_native_batch_size=1`, which turns native batching off. Tests for H5 and H7 need a fixture with native batching on, because that is the default for `mock` and `laya`.
- When an item changes documented behaviour, update the doc it contradicts in the same change.
- Tick the box when the fix and its test are merged.
- Each H item is tracked as a GitHub issue with the same number (H1 is #1 … H9 is #9). Close it from the fixing commit or PR with `Fixes #n`.

## High

### [x] H1. A failed health probe dead-letters every job on that model for the cache TTL [repro r2] ([#1](https://github.com/gellsmore-svg/keziah/issues/1))

- **Where:** `service.py:786-807` (`_execution_target`), `adapters/jev.py:48-61` (the cache), `config.py:57` (`retry_base_s=0.05`).
- **Problem:** Before each call, execution checks the cached health. A transient failure raises a retryable `model_unavailable` without calling the model. Backoff is 0.05 s, then 0.1 s, and the default is 3 attempts, so every job reaches `dead_letter` in about 0.15 s. The failed probe stays cached for 30 s. One 5xx, 429 or timeout on Jev's `GET /v1/models` therefore dead-letters all Jev work for 30 s.
- **Repro:** 5 of 5 jobs `dead_letter` after 0.16 s, with 0 inference calls.
- **Fix:** Pick one of these.
  - (a) When the cached failure is not permanent, attempt the call anyway and let the real call classify the error.
  - (b) Send the job back to `retry_wait` with `not_before` set to cache expiry, without charging an attempt.
  - Keep failing fast for `permanent=True` cases such as a missing key or a 401.
- **Acceptance:** A cached transient failure followed by a working model: the jobs succeed, and none is dead-lettered because of health alone.

### [x] H2. A job whose lease was lost once can never succeed in this process [repro r3] ([#2](https://github.com/gellsmore-svg/keziah/issues/2))

- **Where:** `service.py:110` and `:922` add to `_lost`; `:706` and `:712` check it. Nothing ever removes an entry.
- **Problem:** After one failed heartbeat, the job's later attempts in the same process skip settlement. The lease expires each time and the job ends in `dead_letter` with `lease_expired`. A dispatcher loop stall can cause the first loss; see M2.
- **Fix:** Track lost leases per attempt, for example as `(job_id, owner)` or a per-`_execute` set. Discard the entry in `_execute`'s `finally`.
- **Acceptance:** Simulate one lost lease. The job succeeds on the next attempt and `_lost` is empty afterwards.

### [x] H3. Transitions made by maintenance never wake `wait()` or fire callbacks [repro r4] ([#3](https://github.com/gellsmore-svg/keziah/issues/3))

- **Where:** `service.py:608` throws away the `Maintenance` report. All three backends fill in `report.finished`.
- **Problem:** The affected transitions are a deadline expiring while queued, dead-letter on lease expiry, and cancel on lease expiry. `wait(timeout=None)` then blocks forever. Over HTTP, `/v1/systemone` without `timeout_s` pins an anyio worker thread. In-process callbacks never fire.
- **Repro:** The job failed at 0.3 s. `wait(timeout=3)` returned only at 3.0 s, and the callback did not fire.
- **Fix:** In `_dispatch_loop`, call `self._deliver(job_id)` for each id in `report.finished`.
- **Acceptance:** A queued job with a short deadline behind a blocked job. `wait()` returns `failed` within about one recovery interval of the deadline, and the callback fires.

### [x] H4. `deadline_at` is never parsed or validated [repro r5] ([#4](https://github.com/gellsmore-svg/keziah/issues/4))

- **Where:** `service.py:501` stores the caller's string as given. It is then compared as a string in `queue/common.py:227`, in `queue/sqlite.py:431`, `:671` and `:931`, and in `service.py:683` and `:865`.
- **Problem:** The comparison only works for the exact `YYYY-MM-DDTHH:MM:SS.mmmZ` form. A deadline 30 minutes ahead written with `-05:00` fails immediately. The string `"not a date"` is accepted and never expires. Batch-level `deadline_at` has the same problem.
- **Fix:** In `_build_job` and `submit_batch`, parse with `datetime.fromisoformat`, require a timezone (or reject naive values), normalise with `clock.isoformat`, and raise `ValidationError` (422) on bad input.
- **Acceptance:** A future deadline with an offset runs. Garbage input returns 422. A past deadline gives `failed` with code `deadline`.

### [x] H5. Native batching ignores per-job `parameters`, and Laya's batch path drops them [repro r7] ([#5](https://github.com/gellsmore-svg/keziah/issues/5))

- **Where:**
  - `service.py:558`: `questions_hash` covers the questions only.
  - `service.py:652-663`: companion jobs are coalesced on that hash.
  - `adapters/laya.py:277-295`: `infer_many_blocking` passes no per-item `checkpoint`, `lang`, `task`, `max_len` or `head_max_len`.
- **Problem:** Jobs with different `checkpoint` or `lang` are coalesced, and all of them run on the adapter's default. `Router.predict_batch` in Laya 0.3.20 accepts per-item `model`, `task`, `lang` and `lang_guess`. Native batching is on by default for Laya.
- **Repro:** A job with `{checkpoint: multilingual, lang: fr}` and one with `{checkpoint: english, lang: en}` reached Laya as `predict_batch([{}, {}])`.
- **Fix:**
  - Add a parameters hash to the coalescing key. Either store a separate `params_hash` column, which needs a v3 migration, or hash questions and parameters together for the claim key.
  - In `infer_many_blocking`, map each request's `checkpoint` to `model`, and pass `lang` and `task` per item.
  - `max_len` and `head_max_len` are not per-item in `predict_batch`. Jobs that set them should not be coalesced.
- **Acceptance:** Two jobs with different `checkpoint` values are never in the same native batch. A native batch forwards each item's parameters.

### [x] H6. Graceful shutdown charges an attempt and dead-letters work on its last attempt [repro r8] ([#6](https://github.com/gellsmore-svg/keziah/issues/6))

- **Where:** `service.py:153`, then `queue/sqlite.py:899-915` and `queue/memory.py:520-532`, then `_expire_sql` / `_expire_lease`, whose `attempt_count >= max_attempts` branch dead-letters the job.
- **Problem:** A voluntary release is treated like a crash. Both leased and running jobs keep their incremented `attempt_count`. A job on its final attempt, including any job with `max_attempts=1`, goes to `dead_letter` on a clean shutdown. This contradicts `docs/deployment.md`: "The next start continues queued work."
- **Repro:** A running job with `max_attempts=1`, shut down cleanly, was `dead_letter` on reopen.
- **Fix:** Give `release_leases` its own path. It should return the job to `queued`, decrement `attempt_count` (not below 0), write a `RELEASED` event, and never dead-letter. Add the event to the list in `docs/queue-semantics.md`.
- **Acceptance:** After shutdown and reopen, a released job is `queued` with its attempt count restored, and it then succeeds.

### [x] H7. Group fallback at execution ignores the fallback model's concurrency cap [repro r11] ([#7](https://github.com/gellsmore-svg/keziah/issues/7))

- **Where:** `service.py:741-751` and `:771-774`.
- **Problem:** The slot is reserved on the primary (`model_id`), but the call runs on the fallback's adapter and executor. The fallback's `max_concurrency` is bypassed, and the primary's slot is held while the fallback runs.
- **Repro:** The fallback had `max_concurrency=1`, yet 6 calls ran on it concurrently.
- **Fix:** When `_execution_target` picks a different model, do not run the job in place. Send it back to `queued` with `resolved_model` set to the target and without charging an attempt, so it is claimed through the target's own slots. Alternatively, reserve a slot on the target before calling, and requeue if none is free.
- **Acceptance:** Peak concurrent calls on the fallback never exceed its `max_concurrency`.

### [x] H8. The starvation boost reverses class priority under a sustained backlog [repro r1] ([#8](https://github.com/gellsmore-svg/keziah/issues/8))

- **Where:** `scheduler.py:50-56`, with defaults in `config.py:74-75` (`starvation_boost_cap=8`, `starvation_seconds=10`).
- **Problem:** The boost multiplies each class's own weight by up to 9 times. Once a `normal` backlog is 80 s old it has effective weight 36, against 8 for a fresh `interactive` job. `docs/design-review.md` says "Interactive work still wins more often". `tests/test_scheduler.py::test_old_bulk_gains_share_but_interactive_continues` only asserts that both classes get more than 0 picks.
- **Repro:** Interactive 182 picks, normal 818, out of 1000.
- **Fix:** Make the boost additive and bounded, so that a starving class gains at most a fixed share (for example `weight + boost`, with the boost capped below the top class's weight). Alternatively, cap each class's boosted weight below the base weight of every higher class.
- **Acceptance:** A new scheduler test with a fresh interactive job and a normal or bulk job older than the cap. Interactive gets more than 50% of picks, and the aged class gets more than 0.

### [x] H9. Malformed input returns 500 instead of 422 [repro r6] ([#9](https://github.com/gellsmore-svg/keziah/issues/9))

- **Where:**
  - `api/app.py:274-276`: `request.json()` and `BatchBody.model_validate` run outside `_call`.
  - `service.py:279` and `:285`: `int(...)` on raw NDJSON fields raises `ValueError`.
  - `api/app.py:365-379`: `_call` only catches `KeziahError`.
- **Repro:** A missing `questions`, invalid JSON, and NDJSON with `"priority": "high"` each return 500.
- **Fix:** Catch `json.JSONDecodeError` and `pydantic.ValidationError` and return 422 with code `invalid_request`. In `submit_batch`, validate `priority`, `max_attempts` and `execution_timeout_ms` types explicitly and raise `ValidationError`.
- **Acceptance:** All three repro inputs return 422 with the documented error body.

## Medium

### [ ] M1. `POST /v1/batches` blocks the server's event loop
`api/app.py:260` is `async def`, but it calls `svc.submit_batch` synchronously. That covers validation, registry resolution, which can include a blocking Jev probe, and every SQLite insert for up to 200k rows. `/health/live` and every other route stall for the duration. The body is also buffered in full (`await request.body()` / `request.json()`) before any size check. **Fix:** read the body with a hard byte cap of `max_batch_bytes`, then run `submit_batch` via `run_in_threadpool` (`starlette.concurrency`). Update `docs/batches.md` to say that JSONL over HTTP is buffered, or stream it for real.

### [ ] M2. The Jev health probe blocks the dispatcher loop
`adapters/jev.py:131` makes a synchronous `httpx.get` with a timeout of up to 5 s. It is reached from `service.py:787` (`_execution_target`), `:790-792` and `:896-899` on the asyncio dispatcher thread. Whenever the TTL expires, every model's dispatch and heartbeats freeze, which can cause H2. **Fix:** run the probe off the loop (`asyncio.to_thread`, or refresh the cache in the background) and let execution read only the cache. Add a lock so concurrent callers don't probe at the same time.

### [ ] M3. `/v1/systemone` has no server-side wait cap
`api/app.py:192-193`: with no `timeout_s`, the call waits forever and holds an anyio threadpool thread (about 40 by default). A backlog, or H3, can exhaust the pool and stall every sync route. **Fix:** add a `server.max_sync_wait_s` setting (for example 60 s), use it as the default and the ceiling, and document it in `docs/api.md`.

### [ ] M4. `cancel_on_disconnect` is a stub
`api/app.py:189` and `:386-388` look for an `x-keziah-disconnected` request header, which a client that has gone away can't send. The check also runs only once, before the wait starts. **Fix:** either implement it (an async endpoint that polls `request.is_disconnected()` while waiting on the job) or remove the setting and its sentence in `docs/api.md`. Don't keep a feature that looks as if it works.

### [ ] M5. `queue_ms` includes inference time, so `total_ms` counts it twice [repro r9]
`service.py:812-815`: `queue_ms = now - created_at`, measured at finish. **Fix:** `queue_ms = started_at - created_at`, `total_ms = finished - created_at`. `execution_ms` should be the wall time of the attempt, measured separately from the adapter's `inference_seconds`. The benchmark's `e2e_over_raw` in `bench.py:89-97` inherits this error. Repro: 502 / 501 / 1003 ms with a 500 ms mock.

### [ ] M6. `/metrics` output is invalid Prometheus [repro r10]
`telemetry/metrics.py:310-311` emits `# TYPE` once per label set, so a histogram observed for two models gets two `# TYPE` lines, which Prometheus's text parser rejects. `service.py:333` also increments `keziah_jobs_submitted_total` without labels for batches, but with labels for single jobs. **Fix:** emit `# HELP`/`# TYPE` once per family and group each family's samples together. Label batch submissions with model and class. Add a test that parses `/metrics`; `prometheus_client.parser` can be a dev dependency.

### [ ] M7. O(N) hot paths [repro r12, r13]
- **Memory mode:**
  - `_reserve_capacity` (`queue/memory.py:573`) scans every retained job twice on each submit (repro: 98 µs rising to 1.9 ms per submit at 20k jobs).
  - `maintenance` (`:372`) and `next_wake_s` (`:501`) scan all jobs on every dispatcher wake.
  - `claim_compatible` (`:228`) scans all jobs on every claim.
  - `_jobs_for_batch` (`:606`) scans all jobs on every `wait_batch` poll.

  Keep counters (global and per client), a retry-wait heap, a lease-expiry heap and a per-batch job index.
- **SQLite:** the cancel sweep (`sqlite.py:687`), the deadline sweep (`:668`) and `_reserve_capacity` (`:1135`) all resolve to `SEARCH jobs USING INDEX ... (state=?)`, so they walk every queued row on every wake or submit. Add partial indexes, for example `ON jobs(deadline_at) WHERE state='queued' AND deadline_at IS NOT NULL`, `ON jobs(job_id) WHERE cancel_requested=1`, and `ON jobs(client_id, state)`. Alternatively, keep incomplete counts in a small table updated in the same transaction. This needs a v3 migration.
- **Hybrid:** `reconcile()` (`queue/hybrid.py:33`) reloads every queued row every 2 s on the dispatcher thread, and again on every batch activation. Consider lengthening the interval and adding activated ids incrementally.

### [ ] M8. Execution timeouts in thread mode leave a zombie holding capacity
`service.py:777-784`: `wait_for` times out, but the executor thread keeps running and, for Laya, keeps holding the adapter lock. The slot is released in `_execute`'s `finally`, so the next job queues inside the executor behind the zombie, and its own timeout clock is already running. **Fix:** keep the slot reserved until the underlying future finishes (attach a done-callback that calls `_release`). Report such calls in `/v1/models` `active` so capacity isn't misreported.

### [ ] M9. The one-owner rule for SQLite is not enforced, and `--embedded` breaks it
`cli/main.py:66-70`: `keziah --embedded job|cancel|queue stats|...` opens the default hybrid DB (`~/.keziah/keziah.db`), starts a dispatcher, and runs `_abort_orphan_staging` on open. Beside a running server, it can claim and execute the server's jobs, abort a batch the server is still staging, and use up attempts on shutdown (H6). **Fix:** take an exclusive lock file next to the DB (`fcntl.flock` on `<db>.lock`) in `SQLiteBackend.__init__`, and fail clearly if it is held. Read-only CLI commands should open with `start_workers=False` and skip the orphan sweep.

### [ ] M10. Migrations are not atomic
`queue/sqlite.py:1256-1270`: `executescript` commits implicitly, and the version update is a separate statement. A crash in between leaves tables with no version bump, and the next open fails with "table already exists". Opening a DB whose schema version is newer than the code proceeds silently. **Fix:** run each step as explicit `BEGIN` … DDL … version update … `COMMIT`, not `executescript`, and refuse to open a DB with `schema_version > SCHEMA_VERSION`.

### [ ] M11. Retention doesn't match the docs
- `queue/sqlite.py:822` deletes events by age alone. `docs/queue-semantics.md` says old events go "when their job is already gone", and the memory backend (`memory.py:466`) implements that, so the two backends disagree.
- `batches` rows are never cleaned up.
- `retention.auto_cleanup` and `retention.cleanup_interval_s` are defined in `config.py:94-95` but nothing reads them.

**Fix:** make SQLite match the doc. Delete batches whose jobs are all gone. Either implement periodic auto-cleanup in the dispatcher or remove the two settings.

### [ ] M12. Unbounded in-process maps
- `service.py:956-962`: `_events` never removes entries.
- `_lost` (H2) and `_callbacks` for jobs that are cleaned up without finishing also grow forever.
- `scheduler.py:66`: picker `skips` keeps every `client_id` ever seen.

**Fix:** pop the event in `wait()` once the job is terminal, and prune picker entries for clients with no ready work.

### [ ] M13. Adapter answers are not validated
`adapters/http_common.py:172-188` and `adapters/laya.py:345-364` accept any `answers` dict. A model that leaves out a question, or returns the wrong type, is stored as `succeeded`. **Fix:** after inference, check that `answers` has exactly the requested keys and that each `type` matches. Otherwise raise `PermanentInferenceError(code="invalid_response")`.

### [ ] M14. HTTP adapters open a new client on every call
`adapters/jev.py:93` and `adapters/http.py:269` create an `httpx.AsyncClient` per request, so there is no connection pooling and every decision pays for a TLS handshake. **Fix:** keep one `AsyncClient` per adapter, created lazily on the dispatcher loop, and close it in `shutdown()`. Adapter shutdown is never actually called; see L1.

### [ ] M15. The CLI drops request fields over HTTP
In `cli/main.py:187-200`, `keziah submit file.json` against a server sends only `model`, `state` and `questions`. It drops `parameters`, `client_id`, `priority`, `scheduling_class` and `idempotency_key`, all of which the embedded path passes. **Fix:** pass the same fields in both paths.

## Low

- [ ] **L1.** `registry.shutdown()` (`registry.py:90-94`) looks for `shutdown_sync`, which no adapter defines, and `Keziah.shutdown()` never calls it. Adapters are never closed. Call each adapter's async `shutdown()` on the loop before it stops.
- [ ] **L2.** `service.py:427`: the first assignment to `resolved` in `show()` is dead code, and it triggers extra group-resolution health probes. `show()` raises `ModelUnavailableError` (503) for an unknown model; it should raise `ModelUnknownError`.
- [ ] **L3.** `config.py:275-277` is a no-op `if`, and `seen_aliases` (`:278`, `:289`) is never used.
- [ ] **L4.** `registry.py:203-205`: with a disabled primary and an enabled but unhealthy fallback, the message says "has no enabled model".
- [ ] **L5.** CLI `--mode foo` mutates settings after validation (`cli/main.py:69`, `:91`, `:420`), and `queue/__init__.py:28-30` treats any unknown mode as hybrid. Validate the mode.
- [ ] **L6.** `execution_timeout_ms` and `max_attempts` have no bounds. The server's `Retry-After` value is used without a cap (`service.py:878`); cap it at `retry_max_s` and at the job's deadline.
- [ ] **L7.** The per-client batch capacity check uses only the first row's `client_id` (`queue/memory.py:109`, `queue/sqlite.py:235`), but rows can set their own `client_id`.
- [ ] **L8.** `queue/ready.py:308-314`: re-adding a job id to the same lane leaves a stale heap entry that `_pop_dead` still treats as live. It is harmless until it isn't, so clean it up or track a per-entry generation number.
- [ ] **L9.** The `QueueBackend` Protocol (`queue/backend.py`) leaves out `release_leases`, `find_batch_idempotency`, `claim_by_id` and `ready_candidates`, which the service and hybrid backend call. Add them so pyright checks the contract.
- [ ] **L10.** `/health/ready`, `/docs` and `/openapi.json` are served without auth, but `docs/api.md` says only `/health/live` is open. Either correct the doc or require the token.
- [ ] **L11.** `shutdown()` can wait up to twice `shutdown_grace_s` (`service.py:148-151`), and it stops the loop with tasks still pending ("Task was destroyed but it is pending"). Cancel and await the outstanding tasks before `loop.stop()`.
- [ ] **L12.** Metrics use `inference_seconds`, which the adapter reports, but the Laya batch path splits elapsed time evenly across items (`laya.py:294`). Document this, or record the batch time once.
- [ ] **L13.** `api/app.py:87`: `ErrorBody` is never used. Either use it for the OpenAPI error responses or delete it.

## Test gaps

Add tests for each of these; none exist at `308705e`:

- native batching (fixture with `max_native_batch_size > 1`), including per-job parameters
- deadlines, parsed and expired, plus waking `wait()` on maintenance transitions
- execution timeouts in both `async` and `thread` modes

- cancelling a running job
- group fallback respecting the fallback's capacity

## Fix order

1. **H1, H2, H3, H6.** Small and local; they stop silent data loss and hangs.
2. **H4, H5, H9.** Input and coalescing correctness. H5 needs a schema step.
3. **H7, H8.** Capacity and fairness.
4. **M1–M4.** Server responsiveness and the honesty of documented features.
5. **M5, M6.** Observability.
6. **M7–M15**, then the L items.

Bundle schema changes (H5's parameters hash and M7's indexes) into a single v3 migration, done after M10 makes migrations atomic.
